## 八、上下文成本与工具纪律（强制）

> **依据（实测，非估算）**：某真实项目累计上下文流经 **11.09 亿 tok**，模型实际产出仅约 **313 万 tok**
> （354:1；按缓存 0.1 价折算后仍约 45:1）；平均**每次工具调用背着 24.4 万 tok**；单会话上下文
> 从 38K 涨到 **537K**（中位 304K）。写操作中 **51.5% 是文档更新**（收尾四件套累计 194 次 Edit / 5,551 万 tok）。
> 🔴 **成本公式：总成本 ∝ 轮次 × 上下文长度** —— 两条都要压，只压一条收效有限。

### 八.1 上下文预算（双条件判定，不是单一硬线）

- **单会话单任务**：一个会话只推进一件事；任务完成即收尾并建议换新会话。
  （**不依赖 token 数**——这条比任何阈值都有效，多数浪费来自"一个会话从调研干到部署"）
- **自查点**：每完成一个阶段（约 30 次工具调用）跑一次 `python scripts/ctx_check.py`
  （只读；直接读本会话转录的最新 `prompt_tokens`，不靠猜）
- **分级响应**：

  | 上下文 | 响应 |
  |---|---|
  | < 300K | 正常，不干预 |
  | 300K ~ 500K | **预警**：向用户报告；**开启新的大块工作前**必须先收尾换会话（收尾类小改动可继续） |
  | > 500K | **硬线**：禁止开启任何新工作，只能收尾并换会话 |

- **为什么不用单一硬线**：绝对值不决定成本，**「剩余轮次 × 当前长度」**才决定。大项目在 400K 只做 3 轮收尾是无害的；小任务在 250K 还要做 200 轮探查才是灾难。用单一阈值会把大项目的长任务误伤打断。
- **换会话前**：当前状态写入 `doc/会话交接.md`（只写"未来"），保证新会话可续
- 阈值可调：改 `scripts/ctx_check.py` 顶部 `WARN_TOK` / `HARD_TOK`

### 八.2 读取纪律（大文档先定位、再分页）

- 🔴 **禁止无参数全量 Read 大文档**（> 5K tok）：先 `Grep` 定位，再带 `offset` / `limit` 分页读
- **豁免**：< 5K tok 的文档可直接读（避免把纪律搞成形式主义）
- **写 CHANGELOG 不需要先读全文**：按 §二 在**顶部追加**即可
- 实测教训：规则里写了「开工必读」的 doc/05 反而被全量读最多 —— **「规则要求读」比「文件大」更容易造成全量读**，所以引用它的条款要同步限定

### 八.3 大输出：落盘 + 摘要，不靠截断丢信息

- **原则**：**信息不丢，只是不进上下文**。预估输出 > 100 行的命令，一律：

  ```bash
  cmd > .tmp_cleanup/<名>.log 2>&1
  echo "行数 $(wc -l < .tmp_cleanup/<名>.log)"
  grep -nE "ERROR|FAIL|Traceback|✗" .tmp_cleanup/<名>.log | head -30
  ```

  → 上下文只进「行数 + 命中行」；完整内容留在磁盘（`.tmp_cleanup/` 已 gitignore），需要时随时 Grep / 带 `offset` 定位。**比 `| head` 更省，且零信息损失。**
- `| head` / `| tail` **仅用于本来就只需头尾的场景**（`ls`、`git log`）
- 🔴 **禁止无参数 Read 大 JSON / 大日志**（> 5K tok）：这类内容会**永久留在上下文、之后每一轮都跟着重发**（复利）→ 改用 Grep 取字段
- 单次工具返回 > 8,000 tok 需在回复中说明理由

### 八.4 收尾一次写完（替代 4 次 Edit）

- 🔴 收尾一律用 `python scripts/closeout.py`（见 §二），**不要逐文件手工 Edit** —— 每次 Edit 都要背着整个上下文各跑一轮
- 它同时会体检规则分发（超限 / 漂移 / AGENTS.md 是符号链接）

### 八.5 命令合并 + 子任务审慎

- 同一批探查**合并为一次调用**（`cmd1 && cmd2`，或临时脚本一次跑完），禁止一条条试探
- **禁止重复执行完全相同的命令**（实测同一条命令重复跑了 23 次）——先复用上一步输出
- 子任务有独立冷启动成本（实测每个约 2.5 万 tok）：**< 3 步能做完的不派子任务**
