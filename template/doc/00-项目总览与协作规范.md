## 3. 多 AI 协作规范

### 3.1 规则与记忆的分层（重要，工具无关）

规则**正文只存一份**，但「一份」放在哪取决于**规则规模** —— 见 §3.1.1。各工具的加载情况：

| 工具 | 规则加载方式 | 说明（✅实测 ＞ 📄官方文档 ＞ ❓未验证） |
|---|---|---|
| WorkBuddy / CodeBuddy | 根目录 `AGENTS.md`；`.codebuddy/rules/*.md` 亦自动加载；`.workbuddy/memory/` 为记忆注入 | 三者均✅实测（2026-09-27 / 2026-10-03 某真实项目会话）。⚠️ **根目录 AGENTS.md 的注入段有长度上限、超限静默截断**（实测 8,434 字符时丢尾部两整节），`.codebuddy/rules/` 段**完整无截断** —— 故权威源按规模分档，见 §3.1.1 |
| ZCode | 自动加载根目录 `AGENTS.md`（含符号链接形式） | ✅实测（2026-09-27，某真实项目：AGENTS.md→.codebuddy/rules 软链接被自动注入；ZCode 记忆目录软链接共享 .workbuddy/memory 写读均通） |
| opencode | 自动加载 `AGENTS.md`（为主），`CLAUDE.md` 为兜底 | 📄官方文档（rules 页：两者并存时 AGENTS.md 优先；官方认可 symlink 共享） |
| Claude Code | ≥v2.1.277 **原生读 `AGENTS.md`**（项目内无 CLAUDE.md 时）；旧版/显式场景用 `CLAUDE.md` | 📄官方文档（memory 页）。模板已提供 CLAUDE.md（一行 `@AGENTS.md` 引入，新旧版本通吃）；官方文档明确认可 `ln -s AGENTS.md CLAUDE.md` 符号链接共享 |
| Cursor / Codex / Gemini CLI / Windsurf / Zed | 原生支持 `AGENTS.md`（Cursor 也可用 `.cursor/rules/`） | 📄官方文档（AGENTS.md 开放标准采纳列表） |
| Trae | 自动加载 `.trae/rules/` | ❓**无引入机制**：需复制 AGENTS.md 正文过去（此为唯一允许的复制场景，正文变更时需同步） |
| 其他工具（如 dsh） | 以其官方文档为准 | ❓dsh（DeepSeek Harness）官方文档未确认项目级 AGENTS.md 自动加载（其仓库内 AGENTS.md 仅面向贡献者）；接入前先实测一轮再定（遵循 AGENTS.md 则零配置；有专属路径且无引入机制，才复制正文） |

**去重铁律**：除 Trae 这类无引入机制的工具外，任何入口文件（CLAUDE.md 等）**禁止复制规则正文**，只允许一行引入或符号链接——避免同一规则被多工具重复注入上下文、版本漂移。注意：§3.1.1 模式 B 下的 `AGENTS.md` 是**脚本生成的派生副本**，不属于"手工维护的第二份正文"。

**规则与记忆分离**：规则 = 强制指令（AGENTS.md，人工修订）；记忆 = 知识沉淀（`.workbuddy/memory/`，3000 字符限额，不承载规则）。

### 3.1.1 🔴 规则分发模型（按规则规模分档，2026-10-03 实测修订）

**为什么不能一律放根目录 AGENTS.md**：WorkBuddy 把根目录 `AGENTS.md` 注入到 `<project_guidance>` 段，**该段有长度上限、超限静默截断**（末尾出现 `[...too long, omitted...]`）；而 `.codebuddy/rules/*.md` 走**另一个注入通道**，**完整无截断**。同一份规则、同一会话的实测对照：

| 规则规模 | `AGENTS.md` → guidance 段 | `.codebuddy/rules/` → rules 段 |
|---|---|---|
| 5,376 字符 | 完整 | 完整 |
| **8,434 字符** | 🔴 **被截断**（可见 ≈7,890 字符，丢尾部两整节） | 完整 |

⇒ 上限量级在 **5,400 ~ 7,900 字符**（约 3,300~4,700 tok）之间。机制未完全确定（可能是段长度上限，也可能是 IDE 侧"生成"时的预算），但**两种解释结论一致：不要赌 AGENTS.md 是唯一正文**。

**两种模式**：

| 规则规模 | 权威源 | 其他入口 |
|---|---|---|
| < 5,000 字符（约 3,000 tok） | 根目录 `AGENTS.md`（**实体文件**） | 一行引入 |
| ≥ 5,000 字符 | `.codebuddy/rules/project-rules.md` | `AGENTS.md` 降为**派生副本**（实体文件，供 ZCode 等只认根目录的工具），由 `scripts/sync_rules.py` 保持一致 |

🔴 **禁止的写法**：`.codebuddy/rules/` 只放**一行指针**指向 `AGENTS.md` —— 这会让 WorkBuddy 拿到「被截断的正文 + 一行指针」，**完整规则一节都拿不到**。

**日常操作**：

- 查状态：`python scripts/sync_rules.py --status`（报两侧规模、超限预警、漂移、符号链接风险）
- 同步：`python scripts/sync_rules.py`（默认以 `.codebuddy/rules/project-rules.md` 为权威源）
- 自检：`python scripts/sync_rules.py --check`（不一致时 exit 1，可挂进 CI）
- 收尾自动体检：`scripts/closeout.py` 会顺带报「超限 / 漂移 / AGENTS.md 是符号链接」

**⚠️ 不要用符号链接做项目内的规则入口**：Windows 默认 `core.symlinks=false`，clone 后链接会退化为含目标路径的文本文件（实测 `git checkout` 产出 33 字节文件），**且 git 无法自愈**；建链本身也可能静默降级成 0 字节文件。符号链接只用于「工具全局记忆目录 ↔ 项目记忆」这类项目外场景（见 §3.4）。

**复现上限的方法**：造已知长度的实体 `AGENTS.md` → 开**新会话**（当前会话的注入已固定，改文件观察不到变化）→ 看 system prompt 里 guidance 段末尾有无 `[...too long, omitted...]`；二分即可定出精确上限。

### 3.2 会话生命周期

- **开工**：**定位读** doc/05（只取当前状态，禁止无参全量读 —— 规则 §八.2）→ 读 doc/会话交接.md → 交接板写「当前持有者」→ git pull
- **工作**：每次改动更新 CHANGELOG；排障写调试记录；每约 30 次工具调用跑一次 `python scripts/ctx_check.py`
- **收尾**：**一条命令写完**（替代逐文件手工 Edit）：
  `python scripts/closeout.py --session "<会话名>" --title "<标题>" --body .tmp_cleanup/closeout_body.md --milestone <M编号> --release`
  → 一次完成「CHANGELOG 顶部插入 + doc/05 勾选 + 交接板释放持有者」→ commit + push
- **换会话**：上下文 > 300K 时，**开启新的大块工作前**先收尾换会话；> 500K 是硬线（只能收尾）。换会话前把当前状态写进交接板（只写"未来"）

### 3.3 并发控制

同一时间只允许一个 AI 会话动工（以交接板「当前持有者」为准）。并行开发各自开 feature 分支，主线 main 只由持有者合并。

### 3.4 符号链接桥接（规则入口 / 跨工具记忆共享）

规则正文的权威源位置见 §3.1.1（按规则规模分档）；主流工具原生读取根目录 `AGENTS.md`，**通常无需任何链接**。符号链接只在两种场景需要：

1. **权威源不在根目录**：规则因历史原因放在 `.codebuddy/rules/` 等工具目录时，在项目根建软链接让其他工具读到：
   ```cmd
   mklink AGENTS.md .codebuddy\rules\project-rules.md   :: 在项目根目录执行（相对路径目标）
   ```
2. **其他工具的全局记忆目录接入项目记忆**：各工具记忆目录在用户主目录下（项目外），把其中的索引/流水文件软链接到项目 `.workbuddy\memory\`，实现多工具共享同一份记忆。例（ZCode，在其记忆目录执行）：
   ```cmd
   mklink "C:\Users\<用户>\.zcode\cli\memories\projects\<项目ID>\memory\MEMORY.md" "<项目>\.workbuddy\memory\MEMORY.md"
   ```

**符号链接三坑（全部实测踩过）**：
- **Windows 建链需提权**：管理员 cmd，或开启开发者模式；`mklink` 是 cmd 内置命令，PowerShell 用 `New-Item -ItemType SymbolicLink`
- **跨机器共享盘必须用相对路径目标**：绝对路径（如 `K:\...`）会被客户端拿到本机解析，本机无该盘即读取失败；相对目标则随共享路径正确解析
- **git 仓库内符号链接可移植性差**：Windows 默认 `core.symlinks=false`，clone 后链接退化为含目标路径的文本文件——**项目内链接建议不入库**（按需生成），或团队统一 macOS/Linux 并 `core.symlinks=true`
  - 现场复现：`git checkout -- AGENTS.md` 在 `core.symlinks=false` 下产出 **33 字节普通文件**（内容 = 链接目标路径字符串）
  - 🔴 **退化后 git 无法自愈**：`checkout` 只会再造一个文本文件，恢复必须手工 `cp` 正文
  - 🔴 **创建侧同样危险**：无建链权限时 `ln -s` 与 `New-Item -ItemType SymbolicLink` 会**静默降级为 0 字节文件**（报成功但 `LinkType` 为空）—— 比直接报错更危险，且**回滚不回原状**
  - ⇒ **项目内的规则入口（`AGENTS.md`）一律用实体文件**；符号链接只用于「工具全局记忆目录 ↔ 项目记忆」这类**项目外**场景

**写入穿透限制**：ZCode / Claude Code 的 Edit/Write 工具**拒绝写穿符号链接**（官方行为）——AI 修改规则/记忆时必须直接编辑真实目标文件。因此链接文件只作"读入口"，正文权威路径要在规则中写明。

**记忆共享约定**：`.workbuddy/memory/` 是项目记忆唯一权威源；其他工具的全局记忆目录只放链接不放正文。`MEMORY.md` 为索引（各工具会话自动注入），日期流水文件按需读取；任一工具写入索引/流水即全工具可见（写穿同一权威文件）。

## 4. 质量与验证规范

### 4.1 修复落地验证（强制）

- CHANGELOG 记"已修复"前，必须 **Read 被修改文件**确认改动真实存在（不能只信编辑工具返回值）
- 运行时类修复必须**实际运行验证**，附真实证据；"语法检查通过"不算验证

### 4.2 修复验证方式对照表

| 修复类型 | 必须的验证方式 | 不充分的验证方式 |
|---|---|---|
| 纯逻辑 | 单测 / 静态追踪 | 仅肉眼看代码 |
| 进程/端口 | 实际启动 + 端口检查 | 仅语法检查 |
| HTTP API | 实际请求 | 仅语法检查 |
| 构建/部署 | 实际 build + 运行 | 仅看配置 |
| UI 交互 | 实际打开页面操作 | 仅 build 通过 |

### 4.3 回归预防

修复一处反模式后：① 检查其他文件有无同类问题；② 检查 CHANGELOG 有无"声称已修复但未验证落地"的同类条目。

## 5. 安全红线

- 凭据只进 `.env`（gitignored）；文档代码只写占位符
- 敏感数据不写入任何会外发的 prompt/请求体
- 禁止破坏性命令：`docker system prune -a`、裸路径递归删除、未经确认的批量删除
- 生产环境操作二次确认

## 6. 提交规范

- commit 格式：`<类型>: <摘要>`，类型 = feat/fix/docs/chore/refactor；中文摘要
- 每个逻辑单元一个 commit，不攒大包；推送前确认无凭据泄露
